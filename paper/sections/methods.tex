\section{Study Design}\label{sec:design}
We ran two studies. \textbf{Study~1} (exploratory; 114 synthetic tasks, 2{,}052 trials) surfaced two confounds in our own treatments and an unexpected uptake failure in on-demand documentation. \textbf{Study~2}, the study reported in the rest of this paper, was pre-registered after Study~1. It fixes those confounds, adds real-world tasks derived from KernelBench, and promotes the Study~1 post-hoc conditions to planned ones. Protocol, hashes and all trial logs are released.

\subsection{Fixed IR, toolchain and agent loop}
Programs are StableHLO modules with a single \texttt{@main}. We parse and verify them with the MLIR/StableHLO bindings in jaxlib 0.11.2 (StableHLO 1.20.0) and execute them on XLA:CPU in a sandboxed subprocess with a 60\,s timeout and an operation allow-list: StableHLO plus three CHLO element-wise ops, with no \texttt{custom\_call}. The task fixes the signature exactly. The agent receives a system prompt, the documentation (if any) and the task, and replies with a program. Failures are returned verbatim (verifier diagnostic, or the first mismatching oracle element), with up to two repairs. Documentation stays in context, and in the interactive conditions the retrieval tool remains available (6~calls). Each trial is a fresh conversation at temperature~0, one per task and condition.

\subsection{Canonical facts and interface treatments}
The inventory has 96 facts over 23 operation groups (25 syntax, 16 type, 32 shape, 23 semantics), each anchored to a clause of the pinned specification~\cite{stablehlospec} and authored twice: as a natural-language sentence and as a formal predicate in spec notation. \emph{Study~2 fix~1:} every syntax fact carries the same general schema and the same concrete instance in both renderings (e.g.\ both \texttt{array<i64: ...>} and \texttt{array<i64: 1>}). In Study~1, prose carried only the instance and the formal rendering only the schema. \emph{Fix~2:} the structured contract is compact JSON, so its mean length is $0.98\times$ that of prose over all 328 tasks (Study~1: $1.31\times$). An automated audit checks every task: identical fact-ID sequences, each rendering present verbatim, and no IDs leaking into prose. All 29 code examples verify with the pinned toolchain. A task's fact set is the cross-cutting \texttt{module} facts (program structure, types, the integer-list attribute encoding, no implicit broadcasting) plus the facts of the operation groups the task lists as relevant. Every condition receives the identical task text, signature and list of relevant groups.

\subsection{Tasks and independent oracles}
\textbf{Synthetic (114 tasks).} 38 parametric templates over broadcasting, reductions, contractions, layout, slicing/padding, masking/indexing, conversion and composites (e.g.\ softmax), each instantiated three times with distinct dimension sizes; an additional instance per template is a development split. Each task is specified mathematically, and its oracle is a numpy reference evaluated on three held-out cases that include semantic traps (all-negative rows for max-reductions, exact zeros for strict comparisons, out-of-range \texttt{dynamic\_slice} starts).

\textbf{KernelBench-derived (153 tasks).} We converted all 200 level-1 and level-2 tasks of KernelBench~\cite{ouyang2025kernelbench} (MIT licence): single operators, normalizations, pooling, convolutions, losses, and fused operator chains. The pipeline (i)~shrinks integer size literals deterministically, preserving divisibility when required; (ii)~exposes all module parameters as explicit \texttt{@main} arguments, keeping training-mode semantics as KernelBench evaluates them; (iii)~uses PyTorch eager outputs on three cases, each with freshly initialised parameters and inputs, as the oracle ($\mathrm{rtol}{=}10^{-3}$); and (iv)~produces a reference StableHLO program via \texttt{torch.export} and \texttt{torchax}. The reference is never shown to agents; it only demonstrates that the task is expressible and that the oracle and toolchain agree. The agent sees the PyTorch module source, the argument mapping and the signature. We excluded 24 tasks, each with a logged reason: 18 were too large even after shrinking, 2 had shape couplings broken by shrinking, 2 use dropout, 1 takes a non-tensor input, and 1 failed validation because its reference disagreed with PyTorch. Of the remaining 176, a 10\% hash split (23 tasks) forms the development set, leaving 153 evaluation tasks; the full evaluation population is 267 tasks.

\textbf{Validation (gate G1).} All 328 reference programs (152 synthetic, 176 KernelBench) parse, verify, execute and match their oracles. On synthetic tasks the oracle rejected all 132 non-equivalent executing mutants of the reference solutions; the 13 survivors are semantically equivalent.

\subsection{Models, budget and statistics}
We used three dated snapshots of one family, \texttt{gpt-4.1-nano/-mini/-2025-04-14}. A local Qwen2.5-7B solved 0 of 12 development trials and was not used. The total API budget was capped at \$35 and enforced by the runner. Trials were ordered task-blocked (tasks shuffled, conditions shuffled within each task), so an outcome-blind budget stop leaves complete, paired tasks. The primary endpoint is first-attempt semantic correctness, and the primary contrast is C$-$B. Eight paired contrasts were pre-specified (Table~\ref{tab:contrasts}). For each model we report the mean paired difference with a 95\% cluster-bootstrap CI (10k resamples; clusters are templates for synthetic tasks and individual tasks for KernelBench) and exact McNemar tests, Holm-corrected within each model. Per-suite results are secondary, and the failure taxonomy (assembly syntax, attribute encoding, literal, shape/type, unknown op, wrong values) was fixed before the runs.
